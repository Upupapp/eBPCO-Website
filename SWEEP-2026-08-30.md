## Findings

### Closed

**F-01 — no deploy path.** The site served Netlify's default 404 on every path: the repository had
no build configuration, so Netlify built at the root, which has no `package.json` and no
`index.html`, and published an empty directory. `netlify.toml` now points at the app, pins Node 22
to match the toolchain, and scopes the SPA rewrite.

**F-02 — the site contradicted itself about being official.** The footer and page description
claimed this was the official portal while the contact page named a different site as the
"Official Website". Owner ruling: this portal is the official one. The LGU's main website is still
linked, relabelled.

**F-03 — offices search could not find building permits.** The haystack was name and short
description only, so `building permit`, `building`, `occupancy` and `zoning` returned the empty
state on a building-permit portal. Two different gaps: the first two were listed in the issuing
office's services and never searched; the other two appear nowhere in the office data, so each
office now inherits the names of the permits the permit catalogue states it issues — an assertion
the portal already makes, rather than a new claim about the LGU.

**F-04 — the Announcements control did nothing.** A styled button in the header of every page,
with no handler and no route. Wiring it could not mean writing announcements, since none has been
sourced from the LGU and inventing municipal notices is what the sourcing discipline exists to
prevent. It routes to a page that says so honestly, with the feed injected so the API can replace
one provider rather than the page.

**F-05 — headline figures bypassed their own sourced data.** Population, land area and barangay
count were constants in the component and the census year a literal in the template, so revising
the sourced data changed the label and not the number.

**F-06 — the Mayor's own office page showed no head.** Two data files disagreed about one fact.

**F-07 — placeholder detection was a magic string.** An unconfirmed contact was carried as the
literal `'Pending confirmation'` and the template compared against it; rewording — or translating
— that placeholder would have published it as every unconfirmed office's telephone number.
Modelled as absence now.

**F-08 — no scroll restoration.** Opening an office from part-way down a list landed the reader
part-way down the office page.

**F-10 — office-head avatars showed the first letter of the job title.** Thirteen of seventeen
read "M", the M of "Municipal".

**F-11, F-12 — accessibility.** No skip link; filters conveyed their state by CSS class alone;
filtering announced nothing; the search inputs removed the global focus outline and replaced it
with a ring measuring 1.53:1, under the 3:1 SC 1.4.11 requires. All four closed against the
project's own WCAG 2.1 AA target in `docs/01-Brand-Guidelines/15-Accessibility.md`.

**F-14 — personal contacts published.** Ten office contacts were published from the LGU Citizen's
Charter; four were individuals' personal mailboxes. Owner ruling: withhold those four, keep the
six institutional ones. Only the email is withheld — the telephone numbers are a contiguous
LGU-issued block and were never the concern, so no office was left without a contact route.

**F-15 — wrong URLs answered with the homepage.** `{ path: '**', redirectTo: '' }` meant a
mistyped or retired address quietly rendered the homepage. There is a real not-found page now.
The HTTP status remains 200 and cannot be otherwise: the hosting rewrite serves the shell for
unmatched paths and a client router cannot change a status code. What the client can do is decline
to be indexed, so a directive sets `robots: noindex` for the page's lifetime and removes it on
leave.

**F-16 — 1,252 dead lines and an unused production dependency.** `LiquidEther` reached no page and
was the only consumer of `three`. Deleted rather than wired up: introducing a WebGL fluid
background to a municipal portal is a design decision for the owner and the LGU.

**F-17 — the project's own standards never ran.** `prettier` and a `.prettierrc` were configured
and nothing invoked them. `npm run verify` now chains format check, tests and build.

**F-19 — smaller items.** Scroll-reveal was copy-pasted into three components, which is why F-22
cost three identical edits; it is one directive now. The Building Permit & Occupancy checklist
shipped in every build referenced by no permit, reachable only by guessing its URL. The footer
omitted Permits & Services. Search placeholders measured 2.68:1. No `robots.txt`, sitemap or
social metadata. The repository root had no `.gitignore`, which is how a build cache file came to
be committed.

**F-20 — every path returned 200, including missing files.** A missing form download returned an
HTML page under a `.pdf` filename, so broken links were invisible to any monitor. This is how
three consecutive failed deployments went unnoticed here for two days.

**F-23 — the header brand overlapped the nav between 1180px and 1400px.** At 1280px the two
touched; at 1200px "Home" sat unreadable underneath "Municipality of Castilla". `.brand` carried
`justify-self: start`, which sizes a grid item to its content rather than its track, so the
`min-width: 0` above it never applied and the brand spilled into the nav's track. Found by
rendering the live site — the suite was green and every gate passed throughout. The 1180px
breakpoint's own comment already described this failure and had fixed it only for the case where
the nav is hidden.

**F-24 — the municipality's own name truncated on phones.** At 360px, the most common Android
width, the header read "Municipality of C…". The brand had about 160px once the seal, hamburger
and Announcements button had taken theirs, so the title's ellipsis fired on the one string on the
page that should never be abbreviated. It now wraps instead, below 430px. Pre-existing, and
checked rather than assumed: the prior commit was rebuilt in a detached worktree and truncates
identically.

**F-22 — scroll reveal threw where `IntersectionObserver` is absent**, aborting the lifecycle hook
and blanking the home page's figures. Found by a guard written for F-05, not by reading.

### F-25 — a stale copy of this application existed in another public repository — **CLOSED**

Found 2026-08-30 while trying to locate `ebpco-user-portal` for F-21. **`Upupapp/eBPCO-Web`** —
described as the admin portal — also contains a `castilla-lgu-portal/` directory. It was last
touched on 24 August, six days before the work recorded here, and it is not deployed: that
repository's `netlify.toml` builds `EBPCO WEB ADMIN/E-BPCO-Software-main`, not this app.

It is stale in ways that matter rather than merely out of date. Checked against its HEAD:

- It still carries the `'Pending confirmation'` sentinel that F-07 removed.
- It does not have F-06's `headFromOfficial`, so its Mayor's office page still shows no head.
- **It still publishes one of the four personal email addresses withheld under F-14.**

That last point is the reason this is filed rather than noted. The owner's ruling was to stop
republishing those addresses; they are withheld on the deployed site and at this repository's
HEAD, but a second public repository still carries one at its current HEAD — which is a live
document, not history.

Two things follow. Someone editing the Castilla portal could easily edit the wrong copy and
wonder why nothing changes on the live site. And the F-14 ruling is not fully applied until that
copy is reconciled or removed.

**Closed 2026-08-30 on the owner's instruction:** the directory was deleted from `eBPCO-Web`
(`df98ac5..a69dcba`), which applies the F-14 ruling there too and removes the wrong-copy trap.
Nothing in that repository built it — `netlify.toml` mentioned it only in a comment describing the
monorepo, corrected in the same commit — and the admin portal was rebuilt with the exact Netlify
command beforehand to prove the deletion touched nothing it ships.

One limit worth stating: this removes the addresses from that repository's HEAD, not from its
history. Clearing history would mean rewriting a public repository, which is a separate decision
and has not been taken.

## The contact page map — investigated, not a defect

Worth writing down because it looked like one three times over, and each look
changed the answer.

Under headless Chrome the map frame came back completely blank. Loading the embed URL directly
explained why: it reports *"your browser does not support WebGL"*. OpenStreetMap's embed is
MapLibre GL now and draws nothing without it, and headless Chrome run with `--disable-gpu` has
none.

Re-run with `--headless=new --enable-unsafe-swiftshader`, WebGL2 is available and the picture
changes. A diagnostic injected into the built page reports the iframe at **798×498 inside an
800×500 frame, `src` set** — the layout and the binding are correct — and the embed's zoom
controls and location marker now render inside it. The same URL as a top-level document renders
the full map, tiles and all, correctly centred on the municipal hall.

So the integration works: correct markup, correct sizing, embed loading, marker in the right
place. Only the tile raster fails to paint inside a cross-origin iframe under software WebGL,
which is a property of the harness. **Not reported as a defect.**

One thing did follow from it for real visitors, and has been acted on. The embed has a hard WebGL
dependency, and it was loading on page view — which also meant every visitor's IP address reached
a third party merely by opening the page, on a portal whose privacy notice says it does not
collect personal data. The map is now click-to-load: the panel shows the hall's name, barangay
and road with a button to load the map, and states that doing so contacts OpenStreetMap. Where
WebGL is absent the button is not offered at all, so nobody is invited to open a frame that
cannot draw. The address and Get Directions are present either way.

**The tiles were confirmed too, in the end.** The blank canvas inside the iframe was one more
harness artifact: a cross-origin iframe is site-isolated into its own process, and headless
Chrome does not rasterise WebGL there for a screenshot. Adding
`--disable-features=IsolateOrigins,site-per-process` alongside `--headless=new
--enable-unsafe-swiftshader` makes it render, and with the load button auto-clicked the contact
page draws the full map — Cumadcad, the Maharlika Highway, Inang River, San Vicente, and the
marker on the municipal hall. Nothing about this page is unverified any more.

Home, Offices, Permits, Announcements, About, Local Government, Contact, Privacy and both detail
page types were rendered at 1280px and at 320/360/390/430px. It found **F-23 and F-24**, neither
of which any gate could see, and confirmed F-02, F-07, F-10, F-14 and the F-19 items rendering

Three things it nearly reported and did not, all traced to the harness rather than the site: two

about the renderer until the renderer has been ruled out.

## Two things to know about working here

**No CI, by owner ruling (2026-08-30).** No GitHub Actions, no workflow-scoped credentials, nothing
consuming tokens. The gate is `npm run verify`, run locally by whoever is pushing, as step 4 of the
deploy protocol. A CI workflow was written during this work and deleted when the rule was stated.

**Headless Chrome clamps the CSS viewport to 500px.** `--window-size=390` renders the page at
500px and then crops the screenshot to 390px, so anything in the right-hand 110px looks missing
and text looks clipped mid-word. `--force-device-scale-factor` does not change this. Two apparent
mobile defects — no navigation control, and horizontal overflow — were retracted for this reason
during the F-23 work. The way around it is to render the page inside an **iframe of the target width**, in a window
wider than the clamp: an iframe gets its own CSS viewport, so media queries respond to the real
number. Done that way, 320, 360, 390 and 430 all report `scrollWidth` equal to the viewport with
zero overflowing elements and the navigation control present — and the same method then found
F-24, which the cropped screenshots had hidden.

**Verify a deployment by hash, not by looking.** The site is client-rendered, so grepping the
served HTML shows nothing, and grepping bundles for a UI string gives false negatives when template
interpolation splits the literal. Rebuild the pushed commit and compare artifact hashes against
production. Every deployment above was confirmed that way.
